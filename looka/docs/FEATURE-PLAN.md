## 零、先答一个关键问题：国内用户能用 GPT 吗

**能，而且用户什么都不用做（不需要梯子）。**

原因在架构 —— 用户的手机**从来不直接连 OpenRouter**：

```
用户手机（国内）  ──►  looka.foyue.org        ──►  OpenRouter  ──►  GPT / Claude
                        (Cloudflare Worker)
     ↑ 只需要能连通我们自己的域名        ↑ 这一段在 Cloudflare 网络内部，与 GFW 无关
```

### ✅ 已实测（2026-08-21，从 Worker 内部实发请求）

| 模型 | 结果 | 延迟 |
|---|---|---|
| `openai/gpt-5.6-luna` | ✅ 正常返回中文 | **1168 ms** |
| `openai/gpt-5.5` | ✅ | 1509 ms |
| `anthropic/claude-opus-5` | ✅ | 2542 ms |
| `deepseek/deepseek-v4-pro` | ✅ | 2676 ms |

> **为什么必须实测**：硅基流动国际站 `.com` 就是本机 curl 全通、Cloudflare Worker 里全挂
> （对方对 CF 出口 IP 做了风控），我们为此浪费过一整轮。OpenRouter 此前也只在本机测过。
> 为此新增了常驻探针 `POST /api/admin/probe`（管理口令保护）：
> **任何新上游在写进产品前，都必须先用它从 Worker 内部实测一次。**

### 真正的风险不在这一段

风险在**用户手机 → looka.foyue.org** 这一段：foyue.org 未备案，走 Cloudflare 免费版，
国内流量落在香港/日本/新加坡边缘节点，延迟约 200–400 ms，敏感时期偶有抖动。

但这条链路**今天已经在跑**（小鹿 AI 已经能用），所以不是新增风险。
若将来国内体验恶化，备选：① 朋友公司主体备案后上国内 CDN ② 腾讯云函数中转。

## 一、AI 融入原则：AI 不该是一个 Tab

**现状的问题**：小鹿 AI 是第五个 Tab，用户必须**专门去找它**。
这等于把最有价值的能力藏进了一个抽屉。

**改法**：AI 保留聊天入口，但主要以「每个地方触手可及的一个动作」存在。

| 场景 | 触发 | 小鹿做什么 |
|---|---|---|
| 日历空白处 | 长按 | 「说一句话加日程」——「明天下午三点开会」 |
| 任务 | 右滑 | 拆成 3–6 个子任务 |
| 日记写完 | 底部按钮 | 润色 / 起标题 / 提取今日关键词 |
| 搜索框 | 直接输入 | 自然语言搜索「上个月和张三的会」 |
| 周日晚 | 自动（可关） | 生成「本周回顾」 |
| 月末 | 自动（可关） | 月度总结 + 下月建议 |
| 空白的一天 | **什么都不做** | ⚠️ 见下 |

### ⚠️ 一条硬规矩：小鹿永远不催人

**不做**「你今天还没有安排」「你已经 3 天没写日记了」这类推送。
这与产品定位（一个不催你的地方）直接冲突，是最容易毁掉调性的一步。

小鹿只在**用户主动发起**或**明确开启的周期总结**时出现。

### AI 融入不增加成本

这些全部走**标准模型**（自建通道，边际成本≈0）。
高级/旗舰模型只在用户显式选择时使用。所以 AI 融入是**纯体验收益，零成本**。

## 二、A 档 · 外观 —— Pro 的新主线

> 依据：手帐用户为"好看"付费在现实里（胶带/贴纸/本子）已验证几十年。
> 且这些全是静态资源，**边际成本为 0，可以给得非常厚**。

### A1 · 主题系统扩充 ⭐⭐⭐

现有 `Theme.kt` 已是变量驱动，**扩充是加数据，不是改架构**。

主题 = 一组变量：主色 / 背景 / 纸纹 / 字体 / 图标风格 / 周末色。

| 系列 | 内容 | 归属 |
|---|---|---|
| 九色 | 现有敦煌九色 | 免费 |
| **二十四节气** ⭐ | 每个节气一套配色，跟着农历自动切换 | Pro |
| 敦煌壁画 | 藻井、飞天、鹿王本生 | Pro |
| 莫兰迪 / 暗色 / 极简黑白 | 通用审美 | Pro |
| 每月新增 | 持续更新 | Pro |

**二十四节气是别人抄不了的**——它依赖我们已有的农历系统。这是把
"农历一等公民"这个技术投入，变现成产品差异化的最直接方式。

### A2 · 封面纸 / 背景纹理 ⭐⭐

月视图与日记页的底纹：素色 / 方格 / 横线 / 点阵 / 宣纸 / 敦煌纹样。
技术上就是一张 tileable WebP 做低透明度叠加，几乎零成本、零风险。

### A3 · 字体 ⭐⭐

手帐用户对字体极敏感。免费用系统字体，Pro 给几款手写体 / 宋体 / 圆体。

⚠️ **中文字体 3–8 MB，绝不能打进 APK** —— 必须放 R2 按需下载 + 本地缓存。

### A4 · 自定义 App 图标 ⭐⭐⭐

Android 用 `activity-alias` 实现，**成本为 0**，手帐人群极爱。
性价比最高的一个 Pro 权益。

### A5 · 表情包持续更新 ⭐⭐

每月新增一包（可用第七批的 AI 管线批量产出，我们自己用不计鹿角）。

## 三、B 档 · 深度功能 —— 留住重度用户

### B1 · 智能清单 / 自定义筛选 ⭐⭐

按 标签 + 日期 + 优先级 + 清单 组合出保存的视图（如「本周所有带★的工作任务」）。
数据层加一张 `saved_filters` 表即可，tasks 表不动。

### B2 · 模板 ⭐⭐

- 日记模板：今日三件事 / 感恩日记 / 复盘 / 读书笔记
- 日程模板：周会 / 健身计划 / 旅行行程

免费 3 个，Pro 全部 + 可自建。

### B3 · 统计与年度回顾 ⭐⭐⭐ 最高优先

- 月度：完成率、时间分布、日记字数、表情使用 Top
- **年度回顾长图**：一张可直接发小红书的精美长图

> **这不只是权益，是获客工具。** Spotify Wrapped 效应 ——
> 用户自己会把它发出去，等于免费传播。手帐社群尤其吃这一套。
> 在所有 B 档功能里，这个的投入产出比最高。

### B4 · 附件（图片 / 录音） ⭐⭐

附到日程与日记。存 R2。免费 50 MB，Pro 2 GB。
⚠️ 唯一有真实边际成本的权益，配额制是合理的。

### B5 · 作品导出：精美 PDF / 长图 / 可打印 ⭐⭐⭐

**必须与「数据导出」区分清楚**：

| | 数据导出 | 作品导出 |
|---|---|---|
| 是什么 | JSON / ICS / Markdown，为了带走数据 | 排版精美的 PDF / 长图，为了看和打印 |
| 归属 | **永远免费**（原则 0，基本权利） | Pro |

**手帐用户会想把电子手帐打印出来贴进实体本** —— 这是这个人群独有的需求，
没有哪个日程 App 认真做过。差异化很强。

### B6 · 日历订阅链接（ICS） ⭐⭐

生成一个私密 URL，让 Looka 日程出现在系统日历 / Google Calendar / Outlook。
Worker 输出标准 ICS 即可，**工程量极小、感知很强**。

### B7 · 共享日历（情侣 / 家庭） ⭐

真实需求，但要做权限模型 + 冲突处理，工程量大。放到最后评估。

## 四、新用户礼包（2026-08-21 定）

**注册即赠 30 天 Pro，含 200 次高级模型（GPT-5.6 Luna）体验。**

| 项 | 设计 |
|---|---|
| 成本 | 200 × ¥0.005 = **¥1.0 / 人**，可忽略 |
| 发放 | 注册成功即自动到账，无需领取动作 |
| 防刷 | `plans` 表加 `trial_granted` 标记，一账号仅一次 |
| 到期 | 自动回落免费版，**不自动扣费**（我们本来也没有扣费通道） |
| 提醒 | 到期前 3 天温和提示一次，**不做倒计时焦虑** |

### ⚠️ 最关键的一条：到期不剥夺

- Pro 期间生成的表情、导出的 PDF、写的内容 —— **全部保留可用**
- **Pro 期间启用过的主题，到期后继续能用**（只是不再获得新增的）

这一条很慷慨，但**成本为 0**，却能消除"到期被抢走东西"的恶感。
续费的动机是「每月还有新的」，不是「不续就没收」。这是原则 0 的直接体现。

## 八、对外措辞：不提供应商、不提姊妹站（2026-08-21 提案）

### ⚠️ 先说一条不能照做的

用户要求「隐私说明等都不要说明硅基流动和 zhi.foyue.org」。
**产品文案可以全删，但隐私政策不能一刀切删** ——

《个人信息保护法》第 17 条要求告知处理目的与方式，第 23 条要求向第三方提供个人信息时
**告知接收方名称**。我们确实把用户的日程、日记正文发给了 AI 供应商，
这属于必须披露的事实。删掉等于制造合规缺口，而我们刚补完隐私政策（B21）。

### 分两类处理

| 出现位置 | 处理 |
|---|---|
| **产品内文案**（订阅页、设置页、账号页、营销文案） | ✅ **全部删除**，用户不需要知道我们用谁 |
| **隐私政策的「第三方共享」章节** | ⚠️ **保留但规范化**，见下 |

**隐私政策改法**：不散落在正文里，收进一个独立章节：

> **委托处理与第三方共享**
> 当你使用小鹿 AI 时，你输入的内容及相关日程/日记片段会发送给我们委托的
> AI 服务提供商用于生成回复。我们仅传输完成该功能所必需的内容，
> 不用于其他目的。你可以在「订阅与小鹿 AI」中关闭 AI 读取日程与日记。
> 当前服务商：北京硅基智能科技（硅基流动）、OpenRouter（高级/旗舰模型）。

**zhi.foyue.org / 自知录 的处理不同** —— 它不是第三方，是**同一运营者**的另一个产品，
共用一套账号。所以可以**不点名产品**，改写成：

> 你的登录凭证由本运营者统一的账号服务管理，可能用于本运营者的其他产品。
> 修改密码会对使用同一账号的服务同时生效。

这样既不暴露姊妹站，又如实说明了"改密码会影响别处"这个用户必须知道的事实。

### 需要改的具体位置（共 8 处）

| 文件 | 现状 | 改为 |
|---|---|---|
| `ExtraScreens.kt:179` | 「高级：使用自己的硅基流动 Key 直连」 | 「高级：使用自己的 AI Key」 |
| `ExtraScreens.kt:209` | 「直连硅基流动、走你自己的账单」 | 「直连服务商、走你自己的账单」+ 展开后给获取地址 |
| `AccountScreen.kt:72/499/544` | 「自知录（zhi.foyue.org）」×3 | 「使用同一账号的其他服务」 |
| `Api.kt:52/101` | 注释提及（不可见，可保留） | 保留 |
| `privacy.html` | 硅基流动 ×1、自知录 ×3、zhi ×1 | 按上文规范化 |
| `terms.html` | 自知录 ×1、zhi ×1 | 同上 |

> 💡 自定义 Key 那个入口是给极客用的，**必须**告诉用户去哪申请 key，
> 所以展开后的说明里保留服务商名与链接是合理的 —— 那不是"宣传供应商"，是功能必需。

## 十、品牌：九色鹿的出处要用对

用户指出九色鹿典故出自佛经 —— 这一点之前的文案完全没体现，是个损失。

### 出处（写文案时须准确）

**《佛说九色鹿经》**，三国吴·支谦译；同一故事在本生经中称「鹿王本生」。
最著名的图像是**敦煌莫高窟第 257 窟**的北魏壁画《鹿王本生图》。

**故事**：恒河边有九色鹿，毛具九色、角白如雪。它救起一名溺水者，溺水者立誓不泄露其行踪。
后国王悬赏求鹿，溺水者贪赏告密并引兵围之。九色鹿向国王陈明救人始末，
国王愧悔，下令举国不得伤害九色鹿；背信者身生恶疮。

**内核**：善良、守信、知恩；与背信忘义的对照。

### 能用在哪

| 位置 | 怎么用 |
|---|---|
| **关于 Looka 页** | 用两三句讲清出处与故事，注明《佛说九色鹿经》与莫高窟第 257 窟 |
| **九色主题的命名** | 现在是抽象色名；可改为有出处的名字（恒河、白角、莫高、九色…） |
| **敦煌表情包** | 已存在，可在包简介里点明与鹿王本生的关系 |
| **网站首屏一句话** | 「名字来自敦煌壁画里的九色鹿」——一句就够，不铺陈 |

### ⚠️ 分寸

引用佛经要**准确、克制、注明出处**，不戏说、不把经典当营销素材堆砌。

## 十五、🔒 硬规矩：网页与 App 必须同步

用户 2026-08-21 定：**每次修改都要网页和 App 同步。**

但"所有改动都两端同步"不现实（提醒、小组件网页做不了）。分三类执行：

### ① 必须同步 —— 改一端就必须改另一端，不允许分版本

- **数据结构与同步协议**（`KINDS`、payload 字段）
- **业务规则**（权益、额度、计价、限流）
- **文案与措辞**（走同一份 `i18n/dict-en.tsv`，天然同步）
- **核心视觉**（主题配色、网格线、表情资产、字号层级）

> 违反的后果是**数据不一致或用户认知错乱** —— 比如手机上扣了鹿角、网页上余额没变。

### ② 应当同步 —— 允许延后一个版本，但要挂账

- 交互模式（底栏、选择器、弹窗形态）
- 视图能力（周/日视图、折角提示）
- 次级功能（搜索、分类管理、备份导出）

> 延后必须在 ROADMAP 里留一条待办，**不允许"就这样吧"**。
> 现在的 B1–B8 就是长期不挂账攒出来的。

### ③ 允许单端 —— 平台能力所限

| 只有 App | 只有网页 |
|---|---|
| 精确闹钟提醒、小组件、应用内自更新、FileProvider 安装、触感反馈 | PWA 安装引导、浏览器分享 |

### 检查手段

1. **发版前对照**：改动清单逐条问"另一端呢？"，属于①的必须同批
2. **i18n 天然同步**：新文案只要进 `dict-en.tsv` 就两端都有
3. 建议加一个 `scripts/check_parity.py`：比对两端的功能标记，缺失的报出来
   （目前靠人工，B1–B8 就是这么漏出来的）

### 立刻要还的债

**B1（鹿角/档位）属于①类**（业务规则），本应同批做而没做 —— 这是新规矩确立后的第一笔待还。
不过按第十三节，鹿角要撤出 UI、旗舰下线，所以 B1 会缩小为
「网页 AI 页也要有标准/高级两档选择」，工作量小得多。

## 十六、支付与订阅：更好的方案（2026-08-21 提案）

### 先说结论：现阶段最好的方案是「不接支付网关」

我们有 **0 个付费用户**。接任何自动支付都是过早优化 ——
要处理签约、验签、回调幂等、续费、失败重试、退款、对账，
而这些工程量本可以花在产品上。

**在有 100+ 付费用户之前，「用户付款 → 我们发兑换码」完全够用**：
零费率、零技术风险、随时可换渠道、当天就能收款。这套现在已经跑通了。

### 一个反直觉的建议：不做自动续费，并把它当卖点

我们**没有**自动扣费通道 —— 这本来是限制，但可以变成差异化：

> **Looka 不会自动续费。到期就是到期，我们不会在你忘记的时候扣你的钱。**

理由：
- 「忘记取消被扣钱」是订阅制最大的用户怨念来源
- 与第 0 条（让利于用户）和品牌调性（克制、不催）完全一致
- 到期不剥夺（已定）+ 不自动扣费 = 用户几乎没有风险感，首次付费门槛极低
- 代价是留存靠主动续费 —— 但**如果产品好到用户愿意主动续，那才是真留存**

### 渠道对比（个人开发者视角，无企业主体）

| 渠道 | 个人可用 | 费率 | 微信/支付宝 | 备注 |
|---|---|---|---|---|
| **兑换码 + 收款码** | ✅ | **0%** | ✅ | 人工，但当天可用、零风险 ⭐ 现阶段最优 |
| 爱发电 | ✅ | ~5–8% | ✅ | 合规好、有正规主体；但跳出 App |
| 虎皮椒 / Xorpay | ✅ | 2.8–3.5% | ✅ | ⚠️ 二级服务商，监管收紧，有跑路与关停先例 |

| 应用商店内购 | 需**软著** | 15–30% | ✅ | 见下 |
| 微信支付官方 | ❌ 需主体 | 0.6% | ✅ | 最终目标，等企业主体 |

### 💡 一条被忽略的路径：软件著作权

个人开发者**不需要企业主体**也能上华为 / 小米 / OPPO / vivo 应用市场 ——
只要有**软件著作权**（个人可申请，约 ¥300–1000，30–60 天下证）。

价值不只是支付通道：
- **信任建设** —— 「在应用商店能搜到」对国内用户的心理门槛影响极大，
  远超我们现在"发个 APK 让人侧载"
- 获得正规分发渠道，不再依赖手动发包
- 软著本身也是知识产权保护

代价：抽成 15–30%、要过审核、要处理商店的合规要求（隐私清单、SDK 报备等）。

**建议**：软著现在就可以去申请（下证要 1–2 个月，早申请早有），
但先不急着上架 —— 等产品成熟、有真实用户反馈后再决定。

## 十七、AI 深度融入产品（2026-08-21 提案）

### A · 对话本身的基础体验（用户提出的 + 配套）

| # | 功能 | 说明 |
|---|---|---|
| **A1** | **消息可复制** ⭐ 用户提出 | 长按气泡 → 复制。小鹿给的规划、总结常需要拿走 |
| **A2** | **一键存成笔记** ⭐ | 比复制更进一步 —— 小鹿给的"明天规划"直接存成笔记/日记。**这是把 AI 产出留在产品内的关键**，复制走了就流失了 |
| A3 | 重新生成 | 回答不满意，换一次 |
| A4 | 停止生成 | 配合流式输出 |
| A5 | 编辑并重发 | 问错了不用重打 |
| A6 | 引用某条追问 | 长对话里定位上下文 |

> A2 比 A1 更值得做：**复制是把内容带出产品，存笔记是把内容留在产品里。**

### B · 手帐场景特有的 AI（差异化所在）

这几条别的日程 App 不会做，是我们真正能拉开距离的地方：

| # | 功能 | 为什么值 |
|---|---|---|
| **B1** 🔒**Pro** | **拍照 → 日程** ⭐⭐⭐ | 拍会议通知 / 海报 / 机票 / 快递单，自动提取时间地点建日程。**已验证可行**：`gpt-5.6-luna` 支持 image 输入，单价 $0.20/M，一张图约 +1–2k token ≈ **¥0.003**。手帐用户拍纸质通知是极高频场景 |
| **B2** 🔒**Pro** | **日记 → 自动建议表情** ⭐⭐⭐ | 写完日记，小鹿读出情绪，建议一枚表情贴到当天日历上。**把 AI 和我们 104 枚表情资产连起来了** —— 别人抄不了，因为他们没有这套表情 |
| **B3** | **语音 → 日程/日记** ⭐⭐ | 走路、开车时说一段，转成结构化记录。用系统语音输入 + 现有解析即可，成本≈0 |
| **B4** | **有洞察的月度回顾** ⭐⭐ | 不是罗列数字，而是"这个月你写了 12 篇日记，最常提到工作和跑步；有 3 件事你推迟了 5 次以上——要不要拆小一点？" |
| B5 | 智能重排明天 | 按通勤、精力把日程重排一遍 |
| B6 | 纪念日提取 | 从日记里发现"第一次去了 XX"，问要不要标记 |
| B7 | 行程翻译 | 出国时把日程翻成当地语言（`/api/translate` 逻辑可复用） |

> **2026-08-21 定案：B1、B2 为 Pro 专属功能。**
> 理由：两者都有真实边际成本（B1 每次 ≈¥0.003 的 vision 调用、B2 每篇日记一次模型调用），
> 且都属于「更强」而非「基本权利」，放进 Pro 符合原则 0。
> ⚠️ 但要给免费用户**留一个试用口子**（如每月各 3 次），否则他们根本不知道这功能存在、
> 也就不会为它付费 —— 完全锁死的功能等于没有的功能。

**B1 和 B2 是我最推荐的两个** —— 都用得上已有基建（B1 用现有模型、B2 用现有表情包），
都有明确高频场景，且都是"手帐 AI"而不是"通用 AI"。

### C · 边界（必须同时写死）

- **不主动推送、不催促** —— 已定的硬规矩，AI 融入越深越要守
- **所有 AI 产出都是建议，落库前必须用户确认** —— 现有 action 确认机制已经是这样，不能因为"更智能"就跳过
- **隐私开关要能关掉日记上传** —— 已有；B2（读日记推荐表情）尤其要尊重这个开关
- **拍照识别的图片不留存** —— 传给模型后即弃，不进我们的 R2

### D · 技术改进（体验地基）

| # | 改进 |
|---|---|
| D1 | **流式输出** —— 已在第十二节列为动画优先级第 1 |
| D2 | **上下文更厚** —— 现在只喂近期日程；应加未完成任务、常用地点、作息习惯，「帮我规划明天」才真有用 |
| D3 | **失败要有出口** —— 现在解析失败只有一句"没听懂"，应给「手动创建」按钮兜底 |
| D4 | **两段式调用** —— 散文与动作 JSON 分两次请求（第二次开 `response_format: json_object`），比让模型一次输出混合内容可靠得多 |

### 建议做的顺序

**A1 + A2**（复制 / 存笔记，工作量极小）→ **D1 流式** → **B1 拍照建日程** → **B2 日记推荐表情**

前两步是把现有对话体验补完整，后两步是拉开差异化。

## 十八、Ko-fi + 爱发电 双通道（2026-08-21，用户已注册 Ko-fi）

### 结论先行

**Ko-fi 是纯海外通道，国内用户基本付不了款。** 国内需要另一条腿，
最自然的对称方案是 **爱发电 —— 它就是国内版的 Ko-fi**。

```
海外用户 ──► Ko-fi        （PayPal 收款）
国内用户 ──► 爱发电        （微信 / 支付宝）
                 │
                 └──► 都是「付款 → 我们发兑换码 → App 内输码开通」
                      两条通道汇到同一个已实现的兑换码系统，不需要写支付代码
```

### 为什么 Ko-fi 国内用不了

Ko-fi 的结账走 **PayPal 或 Stripe**：

- **Stripe 结账** 只收 Visa / Mastercard / Amex —— 国内多数人只有银联借记卡，用不了
- **PayPal 结账** 需要用户有 PayPal 账户并绑定可跨境支付的卡
- **不支持支付宝 / 微信**

所以：**Ko-fi = 海外通道**，这个判断是确定的。

### ⚠️ 你需要在 Ko-fi 后台确认的三件事

我无法从 Ko-fi 帮助中心抓到正文（JS 渲染），以下**请你自己核实**，
它们直接决定钱能不能到手：

| # | 要确认的 | 为什么关键 |
|---|---|---|
| **1** | **收款绑的是 PayPal 还是 Stripe** | **Stripe 不支持中国大陆主体**。中国开发者基本只能走 **PayPal**。若后台只让选 Stripe，这条路就断了 |
| **2** | PayPal 中国账户的提现路径与费用 | 收到美元后怎么提到国内银行卡、汇率与手续费多少。**开户前务必先跑通一笔小额**（和 Creem 一样的教训） |
| **3** | Webhook 是不是 Ko-fi Gold（付费）功能 | 决定"自动发码"能不能做。**不能也没关系**，见下 |

### 不需要 Webhook 也能跑（推荐先这样）

**零代码方案**：

1. 在 Ko-fi / 爱发电建一个「Looka Pro · 月度」的会员或商品
2. 商品说明里写：**「下单时请在留言填写你的 Looka 账号邮箱」**
3. 收到订单 → 后台一条命令发码（`/api/admin/gencode` 已实现）
4. 把码回复给用户 / 发邮件
5. 用户在 App「账号与同步 → 兑换码」输入

**全程不写一行支付代码**，当天就能收款。等人工发码开始占用时间了，
再考虑接 Webhook 自动化 —— 那才是该投入的时机。

### 定价要分开定，不能直接换算

¥12/月 ≈ $1.7，但 **PayPal 的固定费（约 $0.30–0.49）在 $1.7 上占 18–29%**，
太狠。海外必须定高一点：

| | 国内（爱发电 / 收款码） | 海外（Ko-fi） |
|---|---|---|
| 月 | **¥12** | **$3** |
| 年 | **¥98** | **$28** |

$3 时 PayPal 抽成约 13%，可以接受。海外贵一些是合理的
（购买力不同 + 支付成本更高 + Ko-fi 不像 Creem 那样代处理 VAT）。

### ⚠️ Ko-fi 与 Creem 的关键差别：VAT

Creem 是 **Merchant of Record**，替我们承担 190+ 国的 VAT/GST 与合规；
**Ko-fi 不是** —— 它只是收款工具，税务责任在我们自己。

对欧盟用户销售数字商品理论上涉及 VAT。**小规模可以先不管**，
但如果海外收入起量了，要么回到 Creem（贵但省心），要么自己处理。
先记在这里，不是现在的问题。

| | **爱发电兑换码** | **我们的兑换码** |
|---|---|---|
| 谁发的 | 爱发电平台 | 我们的 `/api/admin/gencode` |

| 我们能否感知 | ⚠️ **待验证** | 立即生效 |

**爱发电兑换码的用途**：把方案权益**免费送人**（内测用户、朋友、KOL、活动奖品、
用户投诉补偿）。它替代的是"让对方掏钱"，不是"给对方开通 App"。

#### 🔍 待你验证（2 分钟）：兑换会不会产生订单记录

**自己兑换一个，然后看后台订单列表里有没有这一条。**

  送码 = 送 Pro，一步到位，不用我们再发第二次码
- **没记录** → 这 100 个码只能人工走：送码 → 对方兑换 → 告诉我们 → 我们再发 Looka 码

结果决定这批码的用法，先别急着发出去。

### 一、自动开通：自动升级为主，兑换码降级为兜底

**核心判断**：兑换码这一步存在的唯一理由，是我们没法把「支付」和「账号」对上号。
一旦能对上，它就是多余的中间环节 —— 用户付完钱还要翻邮箱、复制、回 App 粘贴，
每一步都在掉人。

```
收到订单
  ├─ remark 能匹配到账号  →  ✅ 直接升级（目标：95% 走这条，用户无感）
  └─ 匹配不上            →  自动发 LOOKA 兑换码到订单邮箱 + 后台标红等人工
```

**兑换码从主流程降级成兜底。** 已建好的系统不浪费，异常单也丢不了。

#### 用一次性绑定码，不要用邮箱

预填邮箱有两个毛病：**把用户邮箱暴露到第三方平台**，且用户容易手改坏。
改用我们生成的短码：

```
① App 点「开通 Pro」
   → POST /api/pay/intent {plan:"month"|"year"}
   → 返回 { code:"LK-8F3A", url:"https://ifdian.net/order/create?...&remark=LK-8F3A" }
② 跳转到该 url（备注已填好）
③ 用户付款
④ Cron 每 5 分钟拉单 → 解析 remark 里的 LK-xxxx → 定位 user_id → 直接升级
⑤ App 回到前台自动刷 /api/me → Pro 已生效
```

短码由我们生成、格式固定、匹配精确，**且第三方平台上留下的不是用户隐私**。

#### 数据结构

```sql
-- 支付意图：把"谁要买什么"和"平台上的一个短码"绑起来
CREATE TABLE pay_intents (
  code       TEXT PRIMARY KEY,      -- 'LK-8F3A'
  user_id    INTEGER NOT NULL,
  plan_days  INTEGER NOT NULL,      -- 31 / 366
  channel    TEXT NOT NULL,         -- afdian | kofi
  status     TEXT NOT NULL,         -- pending | paid | expired
  order_no   TEXT,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);

-- 已处理订单：幂等的唯一依据
CREATE TABLE pay_orders (
  channel    TEXT NOT NULL,
  order_no   TEXT NOT NULL,
  user_id    INTEGER,
  amount     TEXT,
  raw        TEXT,                  -- 原始订单 JSON，出问题时能查
  handled_at INTEGER NOT NULL,
  PRIMARY KEY (channel, order_no)   -- ⚠️ 主键就是防重复的锁
);
```

> ⚠️ **`expires_at` 只用于"不再展示"，匹配时仍然认。**
> 用户可能把付款页放着半小时才付；过期就拒绝开通 = 收了钱不给货，是最糟的 bug。

#### 实现方式：先轮询，不上 Webhook

| | **Cron 轮询 `query-order`** | Webhook |
|---|---|---|
| 验签 | 不需要（我们主动调用） | 要，格式易错且文档抓不到 |
| 重投处理 | 不需要 | 必须做幂等 |
| 公开端点 | 不需要暴露 | 要开一个 |
| 失败重试 | 天然有（下一轮） | 要自己写 |
| 延迟 | ≤5 分钟 | 实时 |

**我们已经有 Cron 了**，加一个 5 分钟任务即可，复杂度比 Webhook 低一个数量级。
5 分钟延迟对"付完钱等一下"完全可接受。有量了再换 Webhook。

> Ko-fi 若只提供 Webhook 而无查询接口，则**爱发电走轮询、Ko-fi 走 Webhook**，
> 两条路互不影响。请到 Ko-fi 后台确认。

#### 异常处理矩阵

| 情况 | 处理 |
|---|---|
| remark 被清空 / 改成别的 | 兜底：发 LOOKA 码到订单邮箱 + 后台标红 |
| 绑定码已过期才付款 | **照常开通**（见上，expires 不参与匹配） |
| 同一用户付两次 | 两条 order_no 都处理 → 叠加续费（`/api/redeem` 已实现叠加逻辑） |
| 轮询/Webhook 重复投递 | `pay_orders` 主键挡住 |
| **退款** | ⚠️ 需单独处理：查到退款订单 → 回收权益。**第一版可先人工**，但要在文档里挂账 |

### 二、客服：建议**不接**第三方聊天 SDK

#### 三个理由

1. **隐私成本** —— 我们刚承诺"你的数据是你的"，引入 Crisp / Tawk 这类 SDK
   就得在隐私政策里加一段第三方采集披露（访客 IP、浏览行为、设备指纹）。
   为一个零用户阶段用不上的功能，削弱刚建立的差异化，不划算。
2. **实时客服对个人项目是陷阱** —— 挂个聊天窗等于承诺"有人在"。
   用户发消息三小时没回，**比没有聊天窗更差**，因为期待被建立了又落空。
   > **一句明确的「24 小时内回复」，好过一个没人守的聊天窗口。**
3. **部分需求已被覆盖** —— 爱发电与 Ko-fi 本身都有留言/私信，
   付费用户天然有渠道找到你。

#### 推荐方案：站内反馈 → 直接推到手机

```
用户填反馈（App / 网页）
   → POST /api/feedback
   → Resend 发到你的邮箱（sendEmail 已实现，几乎零工作量）
   → 可选：同时推一条到飞书/微信机器人，手机秒收
```

**关键设计：提交时自动附带诊断信息** —— 版本号、平台、账号、最近一次错误。
省掉「你用的什么版本」「能截图吗」这种来回，一次就能定位。
现有 `/api/crash` 崩溃收集可以共用同一张表。

#### 先挡掉一半问题：让小鹿当第一层 FAQ

「怎么开通 Pro」「兑换码在哪输」「数据怎么导出」——
这类问题喂一份产品 FAQ 进系统提示词就能自动答，**零额外成本**（我们本来就有 AI）。
答不了的再转人工反馈。

## 二十三、第二轮扫描：运维与数据安全盲区

前一轮（第十四节）扫的是功能与一致性。这一轮扫**出事的时候怎么办** —— 结果不乐观。

| # | 盲区 | 现状 | 后果 |
|---|---|---|---|
| **E1** | **零监控、零告警** | 代码里没有任何告警机制 | **服务挂了我们不知道**，要等用户来说。对付费产品是不可接受的 |
| **E2** | **AI 成本无总量监控** | 有每用户限流（10/分、100/日），但**没有全站总量告警** | key 被滥用或 bug 死循环，等发现时账单已经跑飞 |
| **E3** | **D1 无备份流程** | 没有任何导出/备份脚本 | Cloudflare D1 有 Time Travel（时间点恢复），但**我们从没验证过能不能真的恢复**。没验证过的备份等于没有备份 |
| **E4** | **B18 仍未修** | `markAllDirty()` 把本地全量标脏推送 | **两台设备各自离线用过、再登同一账号 → 产生重复条目**，不是合并。用户会以为是 bug |
| **E5** | 未登录用户零备份 | 有手动导出，但用户不会主动导 | 换手机 = 数据全丢 |
| **E6** | 错误文案太笼统 | 「服务器开小差了，稍后再试」 | 用户不知道该等、该重试、还是该反馈 |

### 优先级建议

**E1 + E2 最该先做，而且很便宜**：
- Worker 里加一个 `/api/admin/health`，返回近 24h 的错误数、AI 调用数、鹿角消耗
- Cron 每天跑一次，异常（如 AI 调用 > 阈值、5xx 率 > 阈值）就用 **Resend 发一封邮件给自己**
- 全部复用已有基建（Cron ✅、sendEmail ✅、D1 ✅），**工作量约半天**

**E3 要做的只是验证**：在测试库上跑一次 D1 Time Travel 恢复，确认流程可行、记下命令。
**没验证过的备份不叫备份。**

**E4 是数据污染类问题**，比功能缺失严重 —— 用户看到重复条目会直接怀疑产品可靠性。
修法：登录时不要无脑 `markAllDirty()`，改为先拉取服务端数据、按 `uid` 比对，
只推送服务端没有的。

## 二十五、🔴 提醒不响：定位与修复方案（2026-08-21 用户报障）

### 已排除的

| 检查项 | 结果 |
|---|---|
| 权限声明（POST_NOTIFICATIONS / USE_EXACT_ALARM / SCHEDULE_EXACT_ALARM / BOOT） | ✅ 齐全 |
| 通知渠道（IMPORTANCE_HIGH） | ✅ 在 Application.onCreate 创建 |
| 三个 Receiver 在 release APK 里 | ✅ 未被 R8 剥离（已解包确认） |
| Android 13+ 运行时申请通知权限 | ✅ MainActivity 有 |
| 新建日程默认插入 Reminder | ✅ `addDefaultReminder` 有 |
| 提醒落库（增/改/删/重复事件） | ✅ 路径完整 |

**代码主链路是通的** —— 所以问题要么在设备侧（权限/ROM），要么在下面这个被我找到的隐性缺陷。

### 🐛 找到一个真缺陷：整批调度会被单条异常打断，且静默无声

`NotifyScheduler.rescheduleFromDb` 把**整个调度过程**包在一个 try-catch 里：

```kotlin
suspend fun rescheduleFromDb(app: LookaApp) {
    try {
        ...
        schedule(app, occs, reminders, tasks)   // ← 循环里逐条 setExactAndAllowWhileIdle
    } catch (_: Exception) {
        // 提醒调度失败不应影响主流程   ← 异常被吞得干干净净
    }
}
```

**问题有两层：**

1. **单点失败 = 整批失败。** `setExactAndAllowWhileIdle` 在权限被系统回收时会抛 `SecurityException`。
   一旦第一条抛出，`for` 循环立刻中断，**后面所有提醒一条都排不上**。
2. **异常被静默吞掉。** 用户看不到任何提示，自检页四项还全是绿的 ——
   因为自检查的是「权限有没有」，不是「闹钟到底排上了没有」。

这完全能解释「四项都正常，但提醒就是不响」。

### 修复方案

**① 逐条容错，别让一条毁一批**
```kotlin
fun setAlarm(t: Long, pi: PendingIntent) {
    try {
        if (exact) am.setExactAndAllowWhileIdle(RTC_WAKEUP, t, pi)
        else am.setAndAllowWhileIdle(RTC_WAKEUP, t, pi)
    } catch (e: SecurityException) {
        failed++          // 记下来，别中断
        am.setAndAllowWhileIdle(RTC_WAKEUP, t, pi)   // 降级重试一次
    } catch (e: Exception) { failed++ }
}
```

**② 记录调度结果，让自检页能看见**
调度完把 `{成功数, 失败数, 下一次触发时间, 上次调度时刻}` 写进 SharedPreferences。

**③ 自检页从「查权限」升级成「查实况」** ⭐ 最关键
现有四项只回答"权限对不对"，加上这三项才能回答"到底排上没有"：

- **已排队提醒：N 条 · 下一次 8 月 22 日 09:00**（没排上就一目了然）
- **上次调度：3 分钟前 / 失败 2 条**
- **🔔「立即测试」按钮** —— 点一下，10 秒后发一条真实通知

> 「立即测试」是整个方案里最有价值的一项：
> **收到 = 通知链路通，问题在调度；收不到 = 通知被系统挡了。**
> 一个按钮就把问题劈成两半，比任何猜测都快。

**④ 200 条上限要提示**
现在超过 200 条静默截断。应在自检页显示「已达上限，最远只排到 X 月 X 日」。

### 仍需你在手机上确认的

代码修完后，若还不响，按这个顺序看（自检页会逐项显示）：
1. 通知权限是否被拒（Android 13+ 弹窗只出现一次，拒了就不再问）
2. 精确闹钟：设置 → 应用 → Looka → 闹钟和提醒
3. **国产 ROM 的自启动 / 后台运行**（小米「自启动」、华为「应用启动管理」改手动、OPPO/vivo「允许后台运行」）—— 这是国内最常见的杀手
4. 电池优化白名单

## 二十六、语音交互 AI：方案对比（2026-08-21 探讨）

用户想要「说一句话，AI 马上干活」的语音体验。查完 OpenRouter 实际能力后，结论如下。

### ❌ 真·实时语音（Realtime API）走不通

OpenRouter **没有任何 realtime 系列模型**（已查证：0 个）。
OpenAI 的 Realtime API 是独立的 WebSocket 服务，OpenRouter 不代理。要用就得：
直接开 OpenAI 账号 + 自建 WebSocket 中转 + 按音频分钟计费 ——
**三样我们都没有，且成本与复杂度都不匹配当前阶段。**

### ✅ 可行的三条路（按推荐度）

#### 方案 A ⭐⭐⭐ 系统 STT + 现有 AI（推荐先做）

```
按住说话 → Android SpeechRecognizer（系统自带，免费）
        → 转成文字
        → 走我们现有的 quickParsePrompt 解析
        → 弹出确认卡片「明天下午3点 开会」
        → 点确认落库
```

| | |
|---|---|
| 成本 | **¥0**（系统能力，国产 ROM 中文识别都很好） |
| 工程量 | 小 —— 一个按钮 + `SpeechRecognizer` + 复用现有解析链路 |
| 体验 | 说完 1–2 秒出结果，**已经很接近"马上干活"** |
| 缺点 | 不是对话式，是"一句话指令" |

**对手帐场景，这个其实够了。** 用户要的多半是「走路时说一句把事记上」，
而不是和 AI 聊天。而且它离线也能用（系统识别引擎多数支持离线中文）。

#### 方案 B ⭐⭐ 音频直传多模态模型（想要"听懂语气"时再上）

OpenRouter 上有 **38 个支持音频输入**的模型，实测价目：

| 模型 | 音频输入单价 | 文本入/出 $/M | 备注 |
|---|---|---|---|
| **google/gemini-3.5-flash-lite** | **$0.0000003/token** | 0.30 / 2.50 | 最便宜 |
| google/gemini-3.7-flash | $0.000000375 | 0.38 / 1.88 | 质量更好 |
| **openai/gpt-audio-mini** | $0.0000006 | 0.60 / 2.40 | **能出音频**（可做语音回答） |
| openai/gpt-audio | $0.000032 | 2.50 / 10.00 | 贵 53 倍，不划算 |

**优势**：直接把录音丢给模型，跳过 STT 环节，能捕捉停顿与语气；
`gpt-audio-mini` 还能**用语音回答**，做到真正的"对话感"。
**代价**：有真实成本、要处理录音上传、延迟比本地 STT 高。

**建议**：作为 **Pro 功能**在方案 A 之后做，而不是替代 A。

#### 方案 C ⭐ 系统 TTS 朗读（顺手加）

`TextToSpeech` 是 Android 系统能力，**零成本**。可以做：
- 小鹿的回答可朗读（开车/做饭时）
- 「今日安排」语音播报

### 建议路线

1. **先做 A**（零成本、工程量小、覆盖 80% 场景）
2. 观察真实使用 —— **如果没人用语音输入，B 和 C 就都别做了**
3. 有需求再上 B（Pro 功能）与 C

⚠️ 与已定规矩一致：**语音不能变成主动打扰**。小鹿不会主动说话，只在用户按下按钮时才听、才答。

## 二十八、AI 还能优化什么（第二轮，2026-08-21）

第十七节写的是「AI 该长在哪些界面」。这一节写**质量本身** —— 同样的功能，
怎么让它更准、更像认识你、更不容易被自己改坏。

### A · 小鹿现在没有人格 ⭐⭐⭐

现有系统提示词里关于"小鹿是谁"只有**一句话**：

> 你是 Looka 手帐应用的 AI 助手「小鹿」，帮用户管理日程、任务、笔记与日记。

没有性格、没有语气边界、没有拒绝方式。结果就是小鹿说话像任何一个通用助手 ——
**而这恰恰是用户对产品「有没有灵魂」的第一感知。**

建议补一段人格设定（纯提示词，**零成本**）：

```
你是小鹿，Looka 手帐里的一只九色鹿。

说话方式：温和、简短、不啰嗦。像一个安静的朋友，不像客服。
   一次说清一件事，不用「首先/其次/总之」这类结构词。

边界：
· 不催促。用户三天没写日记，不要提，也不要暗示。
· 不评判。用户推迟了五次的事，只陈述事实，不说"要加油"。
· 不确定时直说不知道，不猜。
· 用户情绪低落时，先接住情绪，别急着给建议或排日程。

你的名字来自敦煌壁画《鹿王本生图》里的九色鹿 —— 那个故事讲的是善良与守信。
```

最后一句不是文艺 —— **它让模型有一个可参照的性格锚点**，输出会明显更一致。

### B · 完全没有长期记忆 ⭐⭐⭐

已确认：`ai/` 目录下**零记忆机制**。每次对话都从零开始。

用户说过「我不喝咖啡」「周二健身」「不要给我排早上的会」——
下一次全忘光。这是"AI 助手"和"聊天机器人"的分界线。

**建议做一个极简版**（不要上向量库）：

| | 设计 |
|---|---|
| 存什么 | 用户明确表达的**长期偏好**（3–5 条，不是聊天记录） |
| 怎么存 | 新增同步 kind `ai_memory`，一条一句话 |
| 怎么写入 | 小鹿识别到「我一般/我不/我习惯」时**询问是否记住**，用户点确认才存 |
| 怎么用 | 拼进系统提示词，几十 token 而已 |
| 怎么管 | 设置页可查看、编辑、删除 —— **用户必须能看到 AI 记了什么** |

⚠️ **必须用户确认才记**。偷偷记住用户说的话，和我们的隐私立场冲突。

### C · 没有 AI 质量的回归测试 ⭐⭐

`AiActionsTest` 测的是**解析器**（给定字符串能不能解析对），
但没有任何东西测**模型输出**（同样的问题，改完提示词还答得对吗）。

**后果**：每次动提示词都是在盲改。上次 Qwen2.5-7B 的事故就是这么发生的。

建议建一个小的 **prompt 测试集**（20 条典型输入 → 期望特征）：

```
"明天下午3点开会"        → 必须产生 1 个 create_event，date=明天，start=15:00
"今天有什么安排"          → 必须不产生任何 action
"帮我把这周的活拆一拆"    → 必须产生 create_task ≥ 2
"我有点累"               → 不产生 action，且回复不含"建议"二字
```

跑一次约 20 次调用 ≈ ¥0.1。**改提示词前后各跑一遍**，就能挡住 90% 的回归。

### D · 正确性与信任的几个洞

| # | 问题 | 说明 |
|---|---|---|
| D1 | **重复创建无防护** | 用户说两遍"明天开会"，会建两个。应检测同日同名并提示"已存在，要再建一个吗" |
| D2 | **AI 建的东西不能撤销** | 确认落库后就只能手动删。见第二十九节的 Undo |
| D3 | **跨天边界** | 23:50 说"明天"，`dateAnchors()` 算的是当前日期的明天 —— 正确，但**用户心里的"明天"可能是几分钟后的那天**。建议深夜（23:00–04:00）时在提示词里加一句说明 |
| D4 | 长对话截断丢头 | 现在 `slice(-12)` 粗暴截断。应在超长时先做一次摘要压缩 |
| D5 | 无超时取消 | 等太久没法中止（配合流式输出一起做） |

## 二十九、人性化细节：查出来的真实缺口

### 🔴 E1 · 完全没有「撤销」—— 而且它几乎是白捡的 ⭐⭐⭐

已确认：全项目**零 Undo、零回收站、零 Snackbar**。删错一条日程就永久没了。

**但这里有个好消息**：实体里**已经有 `deleted` 软删字段**（同步墓碑用），
服务端也保留 90 天。也就是说 —— **数据本来就还在，只是没有入口。**

建议：
1. 删除后弹一条 Snackbar：**「已删除 · 撤销」**，5 秒内可点回来
2. 设置页加「最近删除」，列出 30 天内删掉的，可恢复
3. 本地删除改为写 `deleted=1`（与同步机制一致），真删交给清理任务

> **这是投入产出比最高的人性化改动**：数据结构现成、同步机制现成，
> 缺的只是一个 Snackbar 和一个列表页。而它解决的是用户最恐慌的场景。

### 🟠 E2 · 编辑到一半退出就丢 ⭐⭐

已确认：草稿只在内存（`draft` 是 ViewModel 字段，无持久化）。
写了半篇日记，来个电话、进程被杀 —— 全没了。

建议：编辑器里**每次输入变更后延迟 500ms 写一份草稿到 SharedPreferences**，
下次进来提示「有未保存的内容，恢复吗」。

### 🟠 E3 · 无障碍：19 处图标没有内容描述 ⭐⭐

`Icon(…, null)` 共 **19 处**（S11 老债）。TalkBack 用户读到的是一片空白，
产品对视障用户等于不可用。

这不只是合规问题 —— **手帐用户里有相当比例是用大字体、高对比度的人**。
顺手要做的还有：大字号下的布局不破、九色主题的对比度检查。

### 🟡 E4 · 语言的温度

| 现在 | 建议 |
|---|---|
| 「2026-08-22」 | **「明天」「后天」「下周三」** —— 三天内用相对表达 |
| 「0 个任务」 | **「今天很轻松」** |
| 空笔记列表：一行灰字 | **一枚表情 + 一句话**（顺便展示我们的资产） |
| 「请求失败 HTTP 500」 | **「小鹿没连上，等会儿再试试」** |
| 空白的一天 | 放当天的**节气或农历**，而不是纯空白 |

### 🟡 E5 · 我们独有的温情能力：农历生日

我们有完整的农历系统 —— **这是别的日程 App 做不好的事**。

- 农历生日提醒（长辈的生日多半记的是农历）
- 节气那天给一句话（**但绝不推送，只在用户打开时看到**）
- 「今天是你记录的第 100 天」这类**温和的看见**，
  ⚠️ 注意分寸：不是"连续打卡 100 天！"（那是压力），而是一句陈述。

### 🟡 E6 · 微交互

- 勾选任务：划线动画 + 轻震（触感反馈是"高级感"最便宜的来源）
- 长按日程：浮层预览，不用进详情页
- 下拉同步：小鹿动画
- 首次启动：3 屏引导，克制版

### 优先级

**E1 撤销** ⭐⭐⭐ —— 数据结构现成，解决最恐慌的场景
**E2 草稿保留** ⭐⭐ —— 防丢内容
**E3 无障碍** ⭐⭐ —— 老债，且影响真实人群
**E4 语言温度** ⭐⭐ —— 纯文案，零技术风险，感知立竿见影
E5/E6 —— 锦上添花

| | Lifebear | Looka 现状（`LIST_PALETTE`） |

#### 换之前必须先修的两件事

**① 白字对比度会炸（真 bug，不是审美问题）**

`CalendarScreen.kt:915` 全天日程色块写死 `color = Color.White`：

```kotlin
Text(o.title, fontSize = 8.sp, color = Color.White, ...)   // 底色 = 分类色
```

Lifebear 盘里 `#F7C212` `#F6DC31` `#DFED38` `#C0E30D` `#59DF86` `#5ED3DA`
`#90DDF7` 等**至少 10 个**是亮色，白字压上去直接看不见。

→ 必须先做**按亮度自动选字色**：

```kotlin
fun onColor(bg: Color) =
    if (bg.luminance() > 0.55f) Ink else Color.White
```

这一处修完，**任何**调色盘都安全 —— 比换色号本身更值钱。

**② 与刚做的纸色主题打架**

v1.5.1 刚把九色主题铺成"纸"（`paperOf` 掺 96% 白，暖色调）。
`#CB00D8` 这种品红压在暖纸上会互相咬。

→ 建议：**日程/清单分类色用 Lifebear 盘**（功能色，要辨识度），
**主题纸色仍走九色鹿**（品牌色，要氛围）。两套色各司其职，不混用。

#### 结论

采纳。顺序：**先修白字对比度 → 再替换 48 色 → App 与网页同步**。

## 三十三、连续滚动 + 爱发电自动开通（2026-08-21 拍板，API 已实测）

### A. 月视图改连续纵向滚动 —— ✅ 用户已拍板

放弃"一屏一个月、左右翻页"，改为 Lifebear 式**跨月无限纵向滚动**。

#### 现状（`CalendarScreen.kt` MonthFull）

```kotlin
val rowH = maxHeight / rows              // ← 行高 = 屏高 ÷ 行数，一个月正好铺满一屏
val maxLines = ((rowH - 17.dp) / 11.dp)  // ← 每格条目数由行高反推
Column(Modifier.verticalScroll(scroll)
    .pointerInput(month) { detectHorizontalDragGestures(...) })  // ← 左右滑切月
for (r in 0 until rows) { Row(Modifier.height(rowH)) { ...7 格... } }
```

#### 目标结构

```
LazyColumn(state)                        ← 以「周」为 item，不是「月」
  └ item(周) = Row { 7 × DayCellV2 }      ← 固定行高
     · 属于当前月 → 纸色底
     · 不属于当前月 → 浅灰底
  └ 每月首个整周背后绘制巨大半透明月份数字（水印）
顶栏标题 ← 由 LazyListState 反推「视口里是哪个月」
```

#### ⚠️ 六个必须先想清楚的点

| | 问题 | 方案 |
|---|---|---|
| **1** | **标题跟谁走？** 滚动中视口同时有 8 月和 9 月 | 取**视口约 1/3 高度处那一行**所属月份；加**滞回阈值**防止边界抖动来回跳 |
| **2** | 🔴 **重复日程展开范围** | 现在只展开当前月网格。连续滚动后必须改成**滑动窗口**（可见范围 ±2 个月），滚动时增量重算。<br>否则要么展开十年（卡死），要么滚过去日程凭空消失。**这是本次最大正确性风险** |
| **3** | **行高不能再由屏高反推** | 必须给固定行高（否则没有可滚内容）。`maxLines` 随之变常量 —— 反而简化。取值要保证一屏≈6 周 |
| **4** | **性能**：`LunarCal.of(day)` 每格调一次（`:534`） | 长滚动会调用上千次，必须加 LRU 缓存 |
| **5** | **左右滑切月手势要删掉** | `detectHorizontalDragGestures`（`:462`）与翻页语义一起消失。删掉后横向手势位空出来，可留给 F6 待办滑动 |
| **6** | 🔒 **网页端必须同步**（§十五 硬规矩） | 网页 `monthGrid` 是静态网格，要改成无限滚动 + `IntersectionObserver` 反推标题。**工作量与 App 相当，不是顺手** |

#### 顺带一起改的（本来就该有）

- 跳转到日期 → `animateScrollToItem`
- 星期头改成 **sticky**，滚动时始终可见

#### 🔴 安全：爱发电 Webhook **没有任何签名**

官方文档的推送格式里，`ec/em/data.order` 全是明文，**没有 sign、没有 timestamp、没有密钥**。
也就是说：**任何人知道了我们的 webhook URL，POST 一个假订单就能给自己开 Pro。**

**正确做法：Webhook 只当"触发器"，绝不当"事实来源"。**

```
收到 webhook
  → 取 out_trade_no（其余字段一律不信）
  → 用我们的 token 签名调 query-order 反查这一单   ← 唯一可信来源
  → 校验 status==2 && remote_id==我们的 user_id
         && plan_id ∈ 我们的方案 && total_amount 与该方案价格相符
  → 幂等落库（out_trade_no 主键）→ 开通
  → 无论成败都返回 {"ec":200}                      ← 否则爱发电会一直重推
```

纵深防御再加两条：
- Webhook 路径带随机段：`/api/pay/afdian/<32位随机>`，别用可猜路径
- 金额校验必须做：防 0.01 元订单开出一年 Pro

#### 🔴 Webhook URL 现在配错了

后台填的是 **`http://foyue.org`** —— 两个问题：
1. **主机错**：`foyue.org` 是选佛谱主站，不是 Looka 的 Worker
2. **协议错**：`http`，应为 `https`

**应改为**：`https://looka.foyue.org/api/pay/afdian/<随机段>`
（改之前先把接口建好并部署，否则"发送测试"必失败）

#### 🔴 `remark` 不可靠 —— 真实订单已经证明了

我们 v1.5.1 的支付入口会把账号邮箱预填进 `remark`。
但**用户这笔真实订单里 `remark` 是手机号 `18664962938`** —— 说明用户可能：
直接从爱发电页面下单（没走我们的链接）、或手动改掉了。

**结论：`remark` 只能当"最优路径"，不能当唯一路径。** 三级兜底：

```
① remark 含 LK-XXXX      → pay_intents 精确命中，直接开通（目标 80%+）
② remark 形似邮箱/手机     → 匹配已注册账号；命中则开通并记日志（本次这笔就属于这类）
③ 都匹配不上             → 存 pay_orders 待认领，后台标红
```

#### 💡 兜底不要发邮件，改「自助认领」

爱发电订单里**没有赞助者邮箱**（`query-sponsor` 也不给），所以"自动发码到订单邮箱"这条
在 §二十一 里其实**走不通**。改成自助认领，反而更快更省事：

```
App/网页「更多 → 我已付款，认领订单」
  → 用户粘贴订单号 out_trade_no（爱发电订单页可复制）
  → 服务端 query-order 反查 → status==2 且未被认领
  → 立即开通，并把 user_id 写进 pay_orders
```

**无需邮箱、无需人工、无需第二套码。** 建议直接替换 §二十一 的"发码到邮箱"分支。

#### 🎯 用户这笔订单现在就能处理

`remark` 是 `18664962938`。**若你的 Looka 账号就是这个手机号，直接按②号路径匹配即可**；
否则用 `/api/admin/gencode` 发一个 31 天码手动兑换。

#### Webhook vs 轮询：结论修正

§二十一 当时定"先轮询不上 Webhook"，理由是"webhook 要验签、要幂等、格式易错"。
**现在证据变了**：webhook 根本没有签名可验（所以也就没有"验签易错"的成本），
而幂等我们本来就要做。

**修正为：Webhook（实时触发）+ query-order（权威校验）+ 每日 Cron 对账（补漏）。**
Webhook 掉一次不要紧，Cron 会捞回来。三层比单层轮询更稳，且延迟从 5 分钟降到秒级。

Cron 要从 `"17 19 * * *"`（每天一次）加一条对账任务；**不需要** `*/5`。

**正确做法：`/` 保持不变，把介绍内容做进 `#authView`（未登录才渲染）。**
登录后、以及 PWA 已安装用户，永远看不到。零路由风险。

### 爱发电宣传位：只在「网页浏览器里」出现

```html

```

// 已安装的 PWA（standalone）视同 App，不展示第三方宣传位
if (window.matchMedia('(display-mode: standalone)').matches) {
