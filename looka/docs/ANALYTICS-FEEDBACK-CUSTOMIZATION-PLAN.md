## 一、先给结论

Looka 现在需要先把统计口径和后台安全做准确，再逐步开放用户建议与定制服务。不要仅按注册人数决定是否开放，也不要一开始就向所有用户承诺“提交后一定开发”。

建议采用以下门槛：

| 阶段 | 建议门槛 | 对用户开放什么 |
|---|---:|---|
| 私下了解需求 | 0—29 名稳定用户 | 一对一访谈、邀请体验、人工记录意见；暂不建立公开需求池 |
| 建议入口 | 30 名稳定用户，连续维持 4 周 | 开放“提交建议”，用户可说明遇到的问题和希望怎样使用 |
| 建议中心 | 100 名稳定用户，且每月不少于 10 条有效建议 | 用户可查看处理状态，并对已有建议点“我也需要” |
| 定制试运行 | 200 名稳定用户，连续维持 8 周，并通过上线前检查 | 限量接受定制申请，每月最多 1—2 项 |
| 正式定制服务 | 500 名稳定用户，并已完成至少 3 项试运行 | 正式展示服务范围、流程和收费方式 |

这里的数字是 Looka 当前阶段的内部经营建议，不是行业统一标准。真正开放时，以“用户数量门槛”和“团队准备条件”同时满足为准。

### 1. 什么叫“稳定用户”

稳定用户不是注册过、打开过应用或只领取鹿角的用户。

建议统一定义为：

> 在最近 28 天内，至少有 6 个不同日期进行过真实手帐行为，并且这些行为分布在至少 3 个不同自然周的用户。

真实手帐行为包括：

- 新建、编辑或完成日程和待办；
- 新建或编辑笔记、日记；
- 整理、回看或搜索自己的手帐；
- 使用贴纸、模板或主题完成一次手帐装扮；
- 使用 AI 后，将结果真正保存进手帐。

以下行为单独发生时不计入稳定用户：

- 只打开应用；
- 只登录；
- 只领取每日鹿角；
- 只浏览订阅页；
- 只与 AI 对话但没有保存到手帐。

这样计算出来的人，才是真正在持续使用 Looka 记录生活的人。

### 2. 为什么不建议一开始就开放定制

定制不是一个普通的“意见箱”。一旦公开，就意味着需要持续回复、评估范围、报价、排期、验收和售后。如果用户量太少，需求可能只是个别偏好；如果团队流程还未准备好，容易让用户期待落空，也会打乱手帐主产品的研发节奏。

因此建议先听取问题，再验证共性，最后才承诺交付。

## 二、产品原则

### 1. 数据是为了改善手帐体验

后台不是为了尽可能多地收集用户数据，而是为了回答几个具体问题：

- 用户是从哪里知道 Looka 的？
- 用户第一次使用时是否理解 Looka 是什么？
- 哪些手帐功能真正被持续使用？
- 用户在哪一步放弃或遇到困难？
- 哪些建议代表共同需求？
- 哪些问题会影响数据安全、同步和长期使用？

### 2. 不读取用户的私人生活内容

分析系统只记录“发生了什么类型的操作”，不记录“用户写了什么”。

不得进入普通分析事件的数据包括：

- 日程标题、待办内容；
- 笔记正文、日记正文；
- 心情内容和私人标签；
- 搜索词；
- AI 对话原文；
- 用户上传的照片和附件；
- 联系方式或定制需求正文。

定制申请是用户主动提交给团队的信息，应单独存储、单独说明用途和保存期限，不能混入普通行为分析。

### 3. 先理解问题，再决定功能

建议入口的重点不是让用户直接写一份产品规格，而是让用户讲清楚：

- 现在遇到了什么不方便；
- 在什么场景下发生；
- 希望最终做到什么；
- 这个问题多久发生一次。

团队根据这些信息判断应该优化文案、修复流程、增加通用功能，还是进入定制评估。

### 4. 不承诺每条建议都会开发

用户提交建议后，Looka 承诺的是“收到、阅读、评估和反馈状态”，不是承诺每条都开发。只有双方确认范围、时间、费用和验收方式后，定制项目才算正式开始。

## 三、当前系统核查结果

### 1. 已经具备的能力

Looka Worker 已有基础事件记录能力，能够记录站点、事件类型、可选用户编号、来源域名、设备类别和时间。当前已有的主要事件包括：

- 落地页浏览、APK 下载；
- 注册、登录、应用打开；
- 支付和支付回调；
- AI 成功与失败；
- 崩溃；
- 邀请或推荐相关行为。

当前实现已经对 Looka Worker 侧的 IP 做按日加盐的 SHA-256 摘要，并限制事件附加信息长度；原始事件保留 90 天、长期保留汇总数据的方向是合理的。

现有 foyue-admin 后台已经具备：

- 总览；
- 用户和订阅；
- 系统健康；
- 子站数据；
- 留存；
- 审计记录；
- 崩溃记录；
- 补开 Pro、绑定订单、生成兑换码、封禁等人工操作。

这些能力可以继续扩展，不需要重新建设一套完全独立的后台。

### 2. 目前的主要问题

| 优先级 | 问题 | 影响 | 建议 |
|---|---|---|---|
| P0 | 后台仍主要依赖一把共享管理密钥 | 无法可靠区分是谁执行了敏感操作，密钥泄露风险较高 | 开放用户建议和定制数据前接入 Cloudflare Access，并保留二次校验 |
| P0 | foyue-admin 公共统计入口使用 btoa(IP + 日期) 截取作为所谓 IP 摘要 | 这不是可靠的加密摘要，不能表述为匿名化 | 改为服务端按日加盐 SHA-256，并定期轮换盐 |
| P0 | 隐私说明尚未覆盖建议、定制申请和更细的产品分析 | 用户不知道会提交什么、为何保存、保存多久 | 开放入口前补充隐私说明和主动同意 |
| P1 | 现有事件集中在获客、登录、支付和 AI | 看不到用户是否真正使用日历、待办、笔记和日记 | 增加不含内容的核心手帐行为事件 |
| P1 | app_open 主要来自已登录用户 | 本地使用、尚未注册的 Android 用户会被遗漏 | 在获得相应同意后，用可重置的匿名分析编号统计，不读取内容 |
| P1 | 当前转化漏斗主要用事件总次数相除 | 同一个人重复打开会造成比例失真 | 改为按唯一用户和同一批用户的阶段转化计算 |
| P1 | 当前留存更接近“之后仍有任意事件” | 容易与严格的 D1、D7、D30 留存混淆 | 明确使用自然日或滚动窗口，并在后台显示定义 |
| P2 | 没有建议、投票、状态和定制申请系统 | 无法形成完整的需求闭环 | 分阶段建设建议与定制中心 |
| P2 | 没有面向单个用户的能力授权模型 | 私有定制容易变成多个代码分支 | 用功能授权和配置控制，不为每个客户复制一套应用 |

### 3. 已有后台数据能回答什么、不能回答什么

现在可以大致回答：

- 最近有多少注册、登录、下载和支付；
- AI 是否成功、是否出现集中失败；
- 是否有崩溃；
- 用户是否在一段时间后再次出现。

现在还不能准确回答：

- 用户是否完成了第一篇日记或第一条待办；
- 日历、待办、笔记、日记中哪个功能形成了习惯；
- 用户从首次使用到稳定使用的真实转化；
- 用户为何流失；
- 哪些空状态、错误或文案最令人困惑；
- 某项建议到底有多少真实手帐用户需要；
- 鹿角获得、使用和兑换是否健康。

所以现阶段不适合直接根据“总注册数”决定产品方向。

## 四、指标体系

### 1. 核心指标

建议 Looka 的核心指标使用：

> 每周真正记录过生活的用户数

配套观察：

- 每名用户每周有记录的天数；
- 最近 28 天稳定用户数；
- 新用户首次完成真实手帐行为的比例；
- 稳定用户中日历、待办、笔记、日记的使用分布；
- 发生同步失败、崩溃或数据恢复的用户比例。

这个指标比“打开次数”更符合 Looka 作为数字手帐产品的定位。

### 2. 指标分组

| 分组 | 需要回答的问题 | 建议指标 |
|---|---|---|
| 获得用户 | 用户从哪里来 | 访问用户、渠道、下载、注册转化 |
| 初次体验 | 用户是否顺利开始 | 首次真实手帐行为、首次完成时间、引导放弃点 |
| 持续使用 | 是否形成习惯 | 周真实记录用户、稳定用户、D1/D7/D30、每周记录天数 |
| 功能价值 | 哪些功能有用 | 日历、待办、笔记、日记、贴纸、主题、AI 的使用人数与复用率 |
| 可靠性 | 是否值得长期托付 | 崩溃用户率、同步成功率、导出成功率、数据恢复事件 |
| 付费 | 用户为何升级 | Free 到 Pro 转化、付费来源、续费和到期 |
| 鹿角 | 通用货币是否健康 | 获得人数、发放量、使用量、余额分布、用途分布 |
| 用户声音 | 用户真正想要什么 | 有效建议数、重复需求数、投票人数、处理时间、采用率 |
| 定制 | 是否值得形成服务 | 有效咨询、完成评估、成交、交付周期、满意度 |

### 3. 留存口径

后台必须同时显示名称和定义，不能只显示一个百分比。

- D1：首次真实手帐行为后的第 1 个自然日，再次发生真实手帐行为；
- D7：首次真实手帐行为后的第 7 个自然日，再次发生真实手帐行为；
- D30：首次真实手帐行为后的第 30 个自然日，再次发生真实手帐行为；
- W1/W4：首周用户在第 1 周或第 4 周仍有真实手帐行为；
- 滚动 28 日稳定用户：符合本文“6 个使用日、跨 3 周”定义的人数。

如果未来采用窗口留存，也必须明确标成“第 7 日附近窗口”或“7 日内回访”，不能与严格 D7 混用。

## 五、事件设计

### 1. 事件命名原则

- 用动作完成后的过去式语义；
- 一个事件只表示一件事；
- 成功和失败分开；
- 不发送用户输入的内容；
- 平台、版本、入口等使用固定枚举，不发送任意长文本；
- 每个指标必须能追溯到事件和计算公式。

### 2. 建议新增的核心事件

| 领域 | 事件示例 | 允许的附加信息 |
|---|---|---|
| 日历 | calendar_viewed、event_created、event_edited | 入口、是否全天、是否重复；不含标题和日期内容 |
| 待办 | task_created、task_completed、task_reopened | 入口、是否有截止提醒；不含任务文字 |
| 笔记 | note_created、note_edited | 入口、是否使用模板；不含正文 |
| 日记 | diary_created、diary_edited、diary_reviewed | 入口、是否含附件；不含正文、心情内容和图片 |
| 装扮 | sticker_used、theme_applied、template_used | 素材编号、来源类型；不含用户图片 |
| 搜索 | search_used、search_empty | 搜索范围、结果数量区间；绝不发送搜索词 |
| 同步 | sync_succeeded、sync_failed、conflict_resolved | 数据类型、错误类别、耗时区间；不含数据内容 |
| 导入导出 | export_started、export_succeeded、export_failed | 格式、数据类型、错误类别 |
| AI | ai_action_succeeded、ai_action_failed、ai_result_saved | 功能类型、模型档位、鹿角消耗；不含对话和生成正文 |
| 鹿角 | antler_earned、antler_spent、antler_redeemed | 数量、用途、来源；不显示内部风控规则 |
| 用户声音 | feedback_submitted、request_supported | 类型、来源入口、需求分类；正文另库存储 |

### 3. 来源参数

只保存白名单字段，例如 source、medium、campaign。不要把完整网址查询参数、个人标识或外部平台可能附带的敏感参数原样写入事件。

### 4. 匿名与登录用户

为了理解未注册用户是否真正开始使用，可在获得相应同意后生成可重置的匿名分析编号。它只用于计算同一安装在一段时间内的产品行为，不读取设备通讯录、广告编号或手帐内容。

用户登录后，后台要避免把匿名阶段和登录阶段重复计算。是否关联两个阶段，应写入隐私说明，并采用最小化做法。

## 六、后台信息架构

建议将后台调整为以下栏目：

| 栏目 | 主要内容 |
|---|---|
| 今日总览 | 稳定用户、真实记录用户、注册、付费、异常和待处理建议 |
| 用户来源 | 渠道、访问、下载、注册和同批用户转化 |
| 产品使用 | 日历、待办、笔记、日记、装扮、搜索、AI |
| 留存习惯 | D1/D7/D30、W1/W4、每周记录天数、稳定用户趋势 |
| 用户 | 账号基本信息、权限、最近操作类型；不显示私人手帐内容 |
| Pro 与收入 | 订阅、订单、续费、退款、渠道 |
| 鹿角 | 发放、使用、兑换、余额分布和异常 |
| 系统健康 | 崩溃、同步、导出、AI、接口异常 |
| 建议 | 新建议、重复需求、投票、状态、回复 |
| 定制 | 申请、评估、报价、排期、验收和售后 |
| 审计 | 管理员身份、时间、动作、对象、理由和结果 |

### 首页只显示真正需要行动的信息

建议首页首屏保留：

- 今日和近 7 日真实记录用户；
- 当前稳定用户数与离下一开放阶段的距离；
- 崩溃、同步和数据安全异常；
- 待回复建议和待处理定制申请；
- 收入和即将到期订阅。

详细图表放到各自栏目，避免后台首页堆满数字却看不出应该做什么。

## 七、“建议与定制”用户流程

### 1. 入口名称

推荐统一名称：

> 建议与定制

不建议仅写“反馈”，因为用户难以判断这里是否能提出新功能；也不建议写“许愿池”，因为涉及定制和费用时显得不够明确。

入口说明：

> 告诉我们你希望 Looka 改进什么，或者申请一项专属定制。

### 2. 两条路径

#### A. 提交功能建议

用户看到的字段尽量少：

1. 你现在遇到了什么不方便？
2. 你希望怎样使用？
3. 发生在什么功能？可选
4. 可以联系你进一步了解吗？可选

提交成功：

> 已收到。我们会认真评估，你可以在这里查看进度。

#### B. 申请专属定制

先说明：

> 请告诉我们你的使用场景和希望实现的结果。我们会先评估范围、时间和费用，双方确认后再开始。

建议字段：

1. 你的使用场景；
2. 希望实现的结果；
3. 谁会使用、大约多少人；
4. 是否有期望时间；
5. 联系方式；
6. 同意团队为评估本申请而使用所提交的信息。

不要让普通用户填写技术方案、数据库字段或页面结构。

### 3. 建议状态

用户可见状态建议保持简单：

| 状态 | 用户能理解的含义 |
|---|---|
| 已收到 | 已经提交成功 |
| 需要补充 | 团队还需要了解一些信息 |
| 评估中 | 正在判断价值、范围和可行性 |
| 已计划 | 已进入后续计划，但不承诺具体日期 |
| 开发中 | 已经开始制作 |
| 邀请体验 | 可以参加小范围测试 |
| 已上线 | 已经可以使用 |
| 暂不计划 | 当前不会安排，并尽量说明原因 |

用户只需要看到简短状态。内部可以有负责人、优先级、成本、风险、依赖和目标版本等更多字段。

### 4. “我也需要”

达到 100 名稳定用户后，再开放“我也需要”。这样可以合并相似需求，看出共同问题。

第一版不建议开放公开评论区。公开评论会增加审核、争吵、隐私泄露和垃圾信息处理成本。用户如需补充，可单独提交或由团队邀请沟通。

### 5. 重复建议

提交时可提示相似建议，但不要强迫用户先搜索。提交后由系统或管理员合并到一个主题，保留每位用户的支持关系和原始私密补充。

## 八、定制服务的产品模式

### 1. 优先顺序

建议按以下顺序承接：

1. 配置型：主题、模板、贴纸包、字段组合和导出格式；
2. 通用增强型：很多用户都需要，资助方可提前使用，成熟后进入公开产品；
3. 接入型：特定导入、导出或第三方服务连接；
4. 私有能力型：只对特定账号或组织开放；
5. 不承接：会破坏隐私、安全、数据可靠性或手帐产品方向的需求。

### 2. 推荐“赞助开发”，谨慎做永久私有分支

如果一个需求符合 Looka 的长期方向，建议采用：

> 用户赞助优先开发，获得提前体验或约定权益；功能成熟后可成为 Looka 的通用能力。

这样既尊重资助者，也不会让主产品被越来越多的私人版本拖住。

必须私有的能力，用账号级功能授权和配置开关控制。不要为每个用户复制一套应用或长期维护独立代码分支。

### 3. 收费与鹿角

- 普通功能建议免费；
- 有价值且被采用的建议、认真完成测试的用户，可以奖励鹿角；
- 不要“提交一条就送鹿角”，否则会制造垃圾建议；
- 标准化的小服务、贴纸、主题和模板未来可以用鹿角兑换；
- 涉及研发工时、长期维护或第三方成本的专属定制，应单独报价，不能只用鹿角模糊定价；
- 报价前必须说明范围、交付物、时间、修改次数、维护期限和退款规则。

### 4. 定制试运行限制

在 200—499 名稳定用户阶段：

- 每月只接 1—2 项；
- 优先选择范围小、能验证共性价值的项目；
- 不承诺紧急交付；
- 每项都要有书面范围和验收标准；
- 完成后复盘实际工时、维护成本和用户满意度；
- 连续出现延期、数据风险或主产品受影响时，暂停接单。

## 九、开放前必须同时满足的条件

达到人数不等于自动开放。定制试运行还必须同时通过以下检查：

### 安全和隐私

- 后台已经使用 Cloudflare Access 或同等级身份保护；
- 敏感操作可以记录到具体管理员，而不是统一显示为 admin；
- 统计入口不再使用 btoa 伪装成匿名摘要；
- 隐私说明已覆盖产品分析、建议和定制申请；
- 用户可以删除自己的建议或申请删除相关信息；
- 手帐正文、搜索词、照片和 AI 原文不会进入行为分析。

### 产品稳定性

- 连续 30 天没有未解决的 P0 数据安全或数据丢失问题；
- 可计算时，同步成功率不低于 99%；
- 可计算时，无崩溃用户比例不低于 99.5%；
- 导出和恢复路径已经过验证；
- 定制功能不会绕开权限、同步和导出规则。

### 运营和交付

- 有明确负责人；
- 普通建议能在 3 个工作日内收到确认；
- 定制申请有评估、范围确认、报价、排期、验收和售后模板；
- 有功能授权机制，不需要维护客户专属代码分支；
- 团队每月确实有 1—2 项定制的可用产能；
- 已说明哪些需求不接受。

如果任何一组未满足，即使达到 200 名稳定用户，也只继续收集建议，不开放付费定制。

## 十、分阶段实施计划

### A0：数据准确与后台安全

- 统一事件、留存、漏斗和稳定用户定义；
- 修复公共统计入口的 IP 摘要方式；
- 后台接入管理员身份保护；
- 敏感操作记录真实管理员；
- 更新隐私说明；
- 明确原始事件、汇总数据、建议和定制资料的保存期限。

验收：后台每个数字都能说明“谁、在什么时间范围、按什么公式”计算；管理入口不是只靠一把共享密钥。

### A1：核心手帐行为

- 为日历、待办、笔记、日记、回看、装扮、同步和导出增加无内容事件；
- 区分打开、真实使用和稳定使用；
- 修正唯一用户转化漏斗；
- 补充严格留存与窗口留存的名称。

验收：可以准确计算本文定义的真实记录用户和稳定用户，抽样核对不读取私人内容。

### A2：用户洞察后台

- 建立产品使用、留存习惯、鹿角和可靠性栏目；
- 支持按版本、平台、地区设置和来源查看；
- 对异常变化设置提醒；
- 首页突出需要行动的问题。

验收：团队每周能回答“用户从哪里来、用了什么、为何可能离开、当前最需要处理什么”。

### A3：30 名稳定用户后开放建议入口

- 上线“建议与定制”入口中的“提交建议”；
- 支持状态和团队回复；
- 合并相似建议；
- 暂不开放公开评论和付费定制。

验收：用户知道提交后会发生什么，也知道不是每条建议都会开发。

### A4：100 名稳定用户后开放建议中心

- 显示适合公开的建议主题；
- 开放“我也需要”；
- 用户可查看自己提交和支持的建议；
- 建立需求分类和月度复盘。

验收：重复需求可以合并，支持人数按真实用户去重，私人补充不会公开。

### A5：200 名稳定用户后进行定制试运行

- 先通过本文第九节全部检查；
- 开放定制申请；
- 每月最多承接 1—2 项；
- 优先配置型和可通用化项目；
- 建立账号级功能授权；
- 记录评估、报价、交付、验收和维护成本。

验收：完成至少 3 项后，能够判断是否按时交付、是否值得维护、用户是否愿意继续使用。

### A6：500 名稳定用户后评估正式开放

只有同时满足以下条件才正式开放：

- 至少完成 3 项定制试运行；
- 最近一个季度至少有 5 个有效定制需求；
- 定制没有明显拖慢主产品；
- 已形成可重复的服务范围和定价；
- 有持续维护和售后能力。

验收：定制是一项可持续服务，而不是临时答应用户后长期背负的项目。

### 每周

- 查看真实记录用户、稳定用户、崩溃和同步异常；

- 复核事件是否仍有必要；
- 删除不再使用的埋点和数据；
- 检查隐私说明与实际行为是否一致；
- 评估定制服务是否影响 Looka 的手帐主线。

## 十三、最终建议

1. 现在就修正数据口径和后台安全，因为用户越多，错误数据和安全债务越难处理。
2. 不必等到 200 人才听取意见；从现在开始就可以做少量一对一访谈。
3. 达到 30 名稳定用户并连续维持 4 周后，再公开“提交建议”入口。
4. 达到 100 名稳定用户并有持续建议量后，再建设公开状态与“我也需要”。
5. 达到 200 名稳定用户、连续维持 8 周，并通过安全、稳定性和交付检查后，限量开放定制试运行。
6. 达到 500 名稳定用户并验证过至少 3 项成功交付后，再决定是否把定制作为正式服务。
7. 无论做到哪一步，都不把用户私人手帐内容用于普通行为分析。
