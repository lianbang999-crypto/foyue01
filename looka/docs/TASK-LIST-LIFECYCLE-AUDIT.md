# Looka 任务与清单全生命周期审计

> 文档状态：讨论稿，不代表已经进入开发或上线
> 审查日期：2026-08-24
> 审查范围：Android App、网页端、Cloudflare Worker／D1、项目母档、执行清单与用户指南
> 审查主题：任务与清单的建立、保存、完成、归档、清除、删除、撤销、同步与恢复
> 本次边界：只记录问题与修复方案，不修改功能代码，不提交，不发布

## 一、结论摘要

Looka 的任务与清单已经具备基础产品骨架：默认清单、自定义清单、任务完成、星标、截止日期、排序、清单归档、任务软删除、清单删除后迁移任务，以及 Android／网页／云端同步实体都已经存在。

但当前还不能认定为“任务与清单链路完整”。本次确认的主要问题不是页面好不好看，而是生命周期中的数据状态会在部分边界断开：

1. 同一批超过 500 条的同步记录会被服务端静默截断，但客户端仍把整批当成成功，存在跨端数据丢失风险。
2. Android 显示“5 秒撤销”，但约 2.5 秒后任务可能已被同步确认并在本地物理删除，后半段撤销窗口不可靠。
3. 网页在“未来 7 天”中新增任务，会把任务写入不存在的 `next7` 清单并立即从页面消失。
4. 删除清单时“迁移任务”和“删除清单”不是同一数据库事务，中断后可能只完成一半。
5. 归档清单仍可新增任务，首页计数与星标／未来 7 天详情页又使用不同筛选口径。
6. Android 有清除已完成任务的数据方法，但没有用户入口；网页有入口，但确认文案与实际清除范围不一致。
7. 任务行声明了“长按删除”，实际没有接入删除手势；已完成任务页也不能打开任务详情。
8. 同步拉取只用毫秒时间作为分页游标，同一毫秒的大批数据可能在分页边界遗漏。
9. 墓碑 90 天后物理删除，但长期离线设备没有过期后强制校准机制，旧任务可能继续留存或再次上传。
10. Android 与网页对“未来 7 天”的天数定义不同，执行清单对网页“已完成清单”的完成状态也记录得过早。

因此，当前更准确的判断是：

- **少量任务的建立、完成和普通编辑：基本可用。**
- **批量数据、删除撤销和清单删除：存在高风险边界。**
- **归档、清除和智能视图：业务口径尚未统一。**
- **跨端同步：有框架，但还没有达到可证明的数据一致性。**

## 三、任务与清单的目标生命周期

### 3.1 任务

| 阶段 | 正确合同 |
|---|---|
| 建立 | 标题合法，归属清单真实存在；从智能视图建立时也必须落入实体清单 |
| 本地保存 | 数据库或本地缓存成功后才提示成功；连续点击不能重复建立 |
| 页面投影 | 建立成功后应在用户预期的位置立即可见；若当前筛选不再匹配，要明确说明去向 |
| 同步上行 | 每一条记录必须获得服务端确认；未确认记录保持待同步 |
| 同步下行 | 同一条任务按明确的冲突规则更新，不产生不存在的清单引用 |
| 完成 | 只改变完成状态与完成时间，不等于删除 |
| 清除 | 明确是当前范围还是全部范围；批量删除仍需可验证、可恢复 |
| 删除 | 先进入可撤销状态，再成为同步墓碑；撤销必须在标称时间内可靠 |
| 物理清理 | 只有确认不再需要恢复且不会破坏其他设备一致性时才执行 |

### 3.2 清单

| 阶段 | 正确合同 |
|---|---|
| 建立 | 名称非空，去除首尾空格；默认清单始终存在且不可删除 |
| 编辑 | 改名、改色和排序不改变清单 UID，不影响已有任务归属 |
| 归档 | 清单仍存在，但是否进入全部／星标／未来 7 天必须有统一规则 |
| 恢复 | 恢复后原任务重新进入活动查询，不改变任务内容 |
| 删除 | 任务迁移与清单墓碑必须在一个事务中完成 |
| 跨端同步 | 其他设备应用清单删除时，也必须保证任务引用得到迁移或降级到默认清单 |

### 3.3 当前实际链路

Android 当前链路：

`Compose 页面 → LookaViewModel → Room DAO → dirty=1 → 2.5 秒静默同步 → /api/sync → D1 items → 下行应用 → 清 dirty／物理清墓碑`

网页当前链路：

`页面事件 → S.data Map → localStorage cache + dirty 队列 → 1.2 秒静默同步 → /api/sync → D1 items → 下行应用 → 重画页面`

现有问题主要发生在“智能视图到实体清单”“撤销到物理清理”“批量上行到服务端确认”“归档到统一查询”这四个连接处。

## 四、已确认的高风险 BUG

### BUG-TL-001 · 超过 500 条的同步记录会被静默丢弃

**优先级：P0；证据级别：L · 代码实证**

服务端只处理上行数组的前 500 条：

- [`server/src/worker.js:929`](../server/src/worker.js#L929)

Android 会先组装全部脏记录，发送一次后确认整个原始数组：

- [`SyncEngine.kt:71-80`](../app/src/main/java/com/looka/app/net/SyncEngine.kt#L71)
- [`SyncEngine.kt:536-599`](../app/src/main/java/com/looka/app/net/SyncEngine.kt#L536)

网页同样会先把整个 dirty 队列移出，发送整批；只要请求没有报错，就不会恢复被服务端截掉的尾部记录：

- [`server/public/app.js:207-226`](../server/public/app.js#L207)

#### 可发生的真实场景

1. 首次登录时本机已有 500 条以上日程、任务、笔记和日记。
2. 一次清除 500 条以上已完成任务。
3. 删除一个包含大量任务的清单，所有任务同时迁移并标脏。
4. 导入较大的备份文件后立即同步。

#### 影响

- 本机显示已经同步，云端实际缺少部分数据。
- 删除墓碑未上传，旧任务继续留在其他设备。
- 本地墓碑被物理删除后，客户端失去再次上传的机会。
- 清单已在云端删除，部分任务仍引用旧清单，形成孤儿任务。

#### 修复建议

1. 客户端把上行拆成每批不超过 500 条，并循环发送直到队列为空。
2. 服务端不要静默 `slice`；超限时应拒绝请求，或者明确返回已接收记录的 UID／版本。
3. 客户端只对服务端明确确认的记录执行清脏或物理删除。
4. 每批失败只重试该批，不得把未确认数据标记为成功。
5. 增加 499、500、501、1000、1001 条的自动化测试。

#### 验收标准

- 1001 条任务可分批完整上传，服务端数量、UID 和内容全部一致。
- 第 2 批网络失败后，第 1 批不重复，第 2／3 批仍保持待同步。
- 1001 条墓碑上传完成前，本地不能提前物理删除未确认记录。

### BUG-TL-002 · 标称 5 秒的任务撤销在自动同步后可能失效

**优先级：P1；证据级别：L · 代码实证，待真机时序验证**

普通任务删除会保存一个内存快照，并显示 5 秒撤销：

- [`LookaViewModel.kt:573-594`](../app/src/main/java/com/looka/app/vm/LookaViewModel.kt#L573)

删除同时会触发静默同步；同步延迟约 2.5 秒：

- [`SyncEngine.kt:44-50`](../app/src/main/java/com/looka/app/net/SyncEngine.kt#L44)

服务端确认墓碑后，Android 会立即物理删除本地任务：

- [`SyncEngine.kt:568-572`](../app/src/main/java/com/looka/app/net/SyncEngine.kt#L568)

撤销实现使用 Room `@Update`。如果记录已被物理删除，`UPDATE` 不会重新插入任务，界面也没有检查受影响行数。

如果撤销发生在同步请求已经发出、但响应尚未回来时，还存在另一种竞态：撤销先把任务改为新版本，随后旧墓碑响应仍无条件物理删除本地任务。

#### 影响

- 用户在界面允许的撤销时间内点击“撤销”，任务仍可能回不来。
- AI 批量删除的撤销账本同样使用旧快照执行 `UPDATE`，也受相似竞态影响。
- 当前 UndoBar 只挂载在清单详情页，星标、未来 7 天等页面删除后可能看不到入口。

#### 修复建议

1. 5 秒撤销期内只进入本地“待删除”状态，撤销期结束后再产生同步墓碑；或者保证撤销使用真正的 upsert。
2. 同步确认删除前，检查本地记录是否仍是同一墓碑版本；若已被恢复或更新，不能物理删除。
3. 将 UndoHost 放到任务模块或应用级 Scaffold，所有删除入口共享。
4. 撤销不是只恢复 UI，必须重新进入同步队列并在其他设备恢复。

#### 验收标准

- 删除后第 1 秒、第 3 秒和第 4.9 秒撤销均成功。
- 在 3G 慢网、同步刚开始、同步刚结束三种时序下均可恢复。
- 从清单、星标、未来 7 天、详情页和 AI 删除后都能看到同一撤销入口。

### BUG-TL-003 · 网页“未来 7 天”新增任务后立即消失

**优先级：P1；证据级别：L · 代码与浏览器实测双重确认**

网页新增任务时，除了 `all` 和 `starred` 之外，直接把当前筛选值当作 `listUid`：

- [`server/public/app.js:1884-1891`](../server/public/app.js#L1884)

因此当前筛选为 `next7` 时，新任务会被写成：

```text
listUid = "next7"
dueDay = -1
```

而“未来 7 天”只显示有日期且位于七天范围内的任务：

- [`server/public/app.js:857-864`](../server/public/app.js#L857)

#### 本次浏览器复现

1. 打开网页版待办。
2. 切换到“未来 7 天”。
3. 输入“浏览器审计任务”并点击添加。
4. 输入框被清空，页面仍显示“还没有任务”。
5. 内存数据中任务存在，但归属为 `next7`，日期为 `-1`。

#### 修复建议

- 智能视图不能成为持久化 `listUid`。
- 从“未来 7 天”快速新增时，建议默认放入“我的清单”，并把日期预填为今天；或者打开任务编辑器让用户选择日期。
- 从“星标”新增可以落入默认清单并自动星标。
- 所有写入入口都要执行“目标清单存在且未删除”的校验。

#### 验收标准

- 从全部、星标、未来 7 天和任意实体清单新增，任务都有有效归属。
- 新任务保存后立即可见；如果因筛选规则不再可见，应明确提示保存到了哪里。

### BUG-TL-004 · 删除清单不是事务，任务迁移只处理未删除记录

**优先级：P1；证据级别：L · 代码实证**

Android 删除清单执行两个独立 DAO 操作：先迁移任务，再给清单打墓碑：

- [`LookaViewModel.kt:615-621`](../app/src/main/java/com/looka/app/vm/LookaViewModel.kt#L615)

DAO 迁移只更新 `deleted = 0` 的任务：

- [`Daos.kt:145-147`](../app/src/main/java/com/looka/app/data/Daos.kt#L145)

#### 风险

- 应用在两步之间退出时，可能只迁移任务但没有删除清单。
- 已软删除任务保留旧 `listUid`；如果之后撤销或从其他设备恢复，会指向已不存在的清单。
- 跨端编辑中的旧任务保存回来时，也可能重新写入已删除清单。
- 当前数据模型没有外键或统一的业务校验阻止孤儿引用。

#### 修复建议

1. 在 Repository／DAO 中提供 `@Transaction` 的“迁移全部引用并删除清单”。
2. 迁移所有仍可能恢复的任务，包括软删除但未物理清理的记录；或者在恢复时强制降级到默认清单。
3. 新增、编辑、复制、AI 创建、备份导入和同步下行统一校验 `listUid`。
4. 应用启动和同步完成后执行轻量完整性扫描：不存在或已删除的清单引用自动降级到 `list-default`，同时保留诊断日志。

#### 验收标准

- 在迁移前、迁移中和清单墓碑写入后模拟中断，最终状态只能是“全部未删除”或“全部迁移并删除”。
- 删除清单后恢复任何旧任务，都只能进入有效清单。

### BUG-TL-005 · 归档清单仍可新增任务，计数与详情页口径不一致

**优先级：P1；证据级别：L · 代码实证**

归档清单仍可从“已完成清单”进入详情页，而清单详情始终显示快速添加框：

- [`TaskListScreens.kt:156-186`](../app/src/main/java/com/looka/app/ui/todo/TaskListScreens.kt#L156)

首页星标与未来 7 天计数会排除归档清单：

- [`TodoScreen.kt:64-75`](../app/src/main/java/com/looka/app/ui/todo/TodoScreen.kt#L64)

但星标页和未来 7 天详情页直接从全部任务中过滤，没有排除归档清单：

- [`TaskListScreens.kt:277-283`](../app/src/main/java/com/looka/app/ui/todo/TaskListScreens.kt#L277)
- [`TaskListScreens.kt:327-335`](../app/src/main/java/com/looka/app/ui/todo/TaskListScreens.kt#L327)

#### 影响

- 首页显示星标 0，进入星标页可能看到归档清单中的任务。
- 用户可以在“已完成清单”中继续建立未完成任务，但这些任务不会出现在主清单入口。
- 网页收到 Android 归档数据后，仍会在“全部、星标、未来 7 天”中显示这些任务。

#### 需要冻结的产品决策

建议采用以下规则：

- “归档”表示整个清单退出日常活动视图，但不删除其中任务。
- 归档清单详情只读；要新增或编辑任务时先恢复清单。
- 全部、星标、未来 7 天默认只显示活动清单任务。
- 已完成任务历史可以继续显示归档清单名称。

如果产品希望归档任务继续出现在智能视图，也可以采用另一套规则，但首页计数和详情必须完全一致，且“已完成清单”不宜继续作为名称。

### BUG-TL-006 · 同步分页使用单一毫秒游标，边界记录可能永久遗漏

**优先级：P1；证据级别：L · 代码实证**

服务端按 `updated_at` 排序，取 1001 条后只返回前 1000 条，再把最后一条的 `updated_at` 作为下一页游标：

- [`server/src/worker.js:959-970`](../server/src/worker.js#L959)

下一页条件是 `updated_at > since`。如果第 1000 条和第 1001 条拥有相同毫秒时间，第 1001 条会因为不大于游标而被永久跳过。

批量清除、清单任务迁移等操作会让多条记录共享同一个 `now()`，因此这不是纯理论问题。

#### 修复建议

- 最稳妥的方式是由服务端生成单调递增的同步版本号。
- 如果继续使用时间，应使用复合游标，例如 `updated_at + kind + uid`，查询与排序也必须使用同一复合顺序。
- 响应返回不透明 `next_cursor`，客户端不自行解释游标结构。

#### 验收标准

- 1001 条记录拥有同一更新时间时，分页后 UID 集合仍完整且无重复。
- 中途重试同一页不会漏数据，也不会导致不可控重复。

## 五、已确认的中优先级问题

### BUG-TL-007 · “清除已完成任务”双端链路不完整

**优先级：P2**

Android ViewModel 有批量软删除方法：

- [`LookaViewModel.kt:596-599`](../app/src/main/java/com/looka/app/vm/LookaViewModel.kt#L596)

但全项目没有界面调用，Android 用户实际无法使用。

网页会清除当前筛选结果中的已完成任务，用户指南也明确写“仅删除当前范围”；但确认弹窗写的是“清除全部已完成任务”：

- [`server/public/app.js:878-888`](../server/public/app.js#L878)
- [`WEB-USER-GUIDE.md:182`](WEB-USER-GUIDE.md#L182)

#### 建议合同

提供两个明确动作，而不是用模糊的“全部”：

- 在实体清单内：`清除这个清单中已完成的任务`。
- 在已完成任务总页：`清除全部已完成任务`。

批量清除应显示数量，并进入可恢复的批次墓碑；不能逐条重画页面、逐条安排同步。

### BUG-TL-008 · 任务行的删除参数未接线，部分页面无法进入删除链路

**优先级：P2**

`TaskRowV2` 接收 `onDelete`，注释写着“长按删除”，但组件内部没有使用该回调：

- [`TaskListScreens.kt:515-584`](../app/src/main/java/com/looka/app/ui/todo/TaskListScreens.kt#L515)

同时，清单页长按已经用于拖拽排序，不能再无规则地复用为删除。已完成任务页的行点击是空函数，搜索结果和日历日面板中的任务也只能切换完成，不能打开详情。

#### 建议

- 保留“任务详情 → 更多 → 删除”为统一主路径。
- 清单页如需要快捷删除，使用明确的滑动操作或行尾菜单，不与长按排序冲突。
- 已完成任务、搜索结果和日历日面板中的任务行都应能打开同一任务详情。
- 删除入口共享同一确认、撤销和同步实现，不允许各页面自行删除。

### BUG-TL-009 · 删除确认规则不一致，撤销入口也不是全局的

**优先级：P2**

任务详情页“更多 → 删除”会二次确认：

- [`TaskDetailScreen.kt:185-190`](../app/src/main/java/com/looka/app/ui/todo/TaskDetailScreen.kt#L185)

但任务编辑弹窗底部的“删除”会直接执行：

- [`TaskListScreens.kt:753-757`](../app/src/main/java/com/looka/app/ui/todo/TaskListScreens.kt#L753)

普通任务 UndoBar 只挂载在清单详情页：

- [`TaskListScreens.kt:266`](../app/src/main/java/com/looka/app/ui/todo/TaskListScreens.kt#L266)

#### 建议合同

- 明确的“删除”按钮统一二次确认。
- 滑动等高误触动作可以不再弹窗，但必须提供可靠撤销。
- 所有页面共用一个应用级 UndoHost，撤销时显示对象名称和剩余时间。

### BUG-TL-010 · Android 任务建立页的草稿与防重复保护不完整

**优先级：P2**

日程编辑器中的任务模式保存了独立的 `taskTitle`、`taskMemo` 等状态，但关闭页面时只检查日程草稿字段：

- [`EventEditorScreen.kt:103-121`](../app/src/main/java/com/looka/app/ui/event/EventEditorScreen.kt#L103)
- [`EventEditorScreen.kt:131-140`](../app/src/main/java/com/looka/app/ui/event/EventEditorScreen.kt#L131)

因此用户在任务模式写了一半后按关闭或系统返回，可能直接丢弃，不出现放弃确认。任务模式保存也没有复用日程模式的 `saving` 防连点保护：

- [`EventEditorScreen.kt:182-188`](../app/src/main/java/com/looka/app/ui/event/EventEditorScreen.kt#L182)

#### 建议

- Dirty State 必须按当前模式检查对应字段。
- 任务保存开始后锁定按钮，收到本地写入成功回调后再退出。
- ViewModel 的 `addTask` 返回结果，不要让页面在不知道写入是否成功时先提示“已添加”。

### BUG-TL-011 · 清单名称校验双端不一致

**优先级：P2**

Android 使用 `isBlank()`，全空格名称不会建立；网页先用 `if (!name)` 判断原始输入，再执行 `trim()`，因此全空格可以建立一个空名称清单：

- [`server/public/app.js:848-852`](../server/public/app.js#L848)

重复名称目前两端都允许。重复名称不一定是 Bug，但需要作为明确产品选择；如果允许，应在删除和迁移确认中显示颜色或任务数量帮助区分。

### BUG-TL-012 · “未来 7 天”在 Android 与网页端实际是不同范围

**优先级：P2**

Android 使用 `(0..7)`，表示今天以及之后 7 天，共 8 个日期：

- [`TaskListScreens.kt:330-335`](../app/src/main/java/com/looka/app/ui/todo/TaskListScreens.kt#L330)

网页使用 `dueDay >= today && dueDay < today + 7`，表示今天起共 7 个日期：

- [`server/public/app.js:857-861`](../server/public/app.js#L857)

用户指南写的是“今天起 7 天内”：

- [`WEB-USER-GUIDE.md:174`](WEB-USER-GUIDE.md#L174)

建议以用户指南为准：今天、明天以及之后 5 天，共 7 个日期。逾期任务可以在页面顶部单独显示，但不应混入“未来 7 天”的数字而不说明。

## 六、长期离线与墓碑清理缺口

### RISK-TL-001 · 离线超过 90 天的设备可能永远收不到删除

**优先级：P1 设计风险；证据级别：L · 代码实证，需端到端验证**

服务端每天删除 90 天以前的墓碑：

- [`server/src/worker.js:1417-1423`](../server/src/worker.js#L1417)

如果某设备在墓碑产生后一直离线，超过 90 天再上线：

- 服务端已经没有该墓碑。
- 客户端本地仍保留旧任务。
- 仅把拉取游标重置为 0，也无法通过“云端没有这条记录”推断本地应删除。
- 用户随后编辑旧任务时，可能把它重新上传到云端。

#### 修复建议

1. 服务端记录“可增量同步的最早版本”。
2. 客户端游标早于该版本时，服务端返回 `full_reconcile_required`。
3. 全量校准必须有清晰语义：先安全保存本地未同步修改，再以服务端现存 UID 清单校准已确认的旧记录。
4. 或者为每个设备维护同步确认点，只有所有活跃设备都确认后才清墓碑。

隐私政策中的“墓碑至多保留 90 天”可以继续成立，但删除物理数据与跨设备一致性需要配套协议，不能只靠延长保存时间。

## 七、备份恢复中的任务归属缺口

### RISK-TL-002 · Android 合并已有任务时没有恢复全部任务字段

Android 从备份导入一个“本地已经存在、备份版本更新”的任务时，只覆盖标题、完成状态、日期和备注，没有覆盖 `listUid`、星标、完成时间和排序：

- [`Backup.kt:208-213`](../app/src/main/java/com/looka/app/util/Backup.kt#L208)

这会造成备份里已经移动到新清单的任务，恢复后仍留在旧清单。建议把任务可导出的全部业务字段纳入同一合并合同，并对不存在的清单归属降级到默认清单。

## 九、建议冻结的任务与清单业务合同

### 9.1 建立任务

- 任务标题去除首尾空格后不能为空。
- 每个任务必须属于一个真实、未删除的实体清单。
- 从全部建立：进入默认清单。
- 从星标建立：进入默认清单并自动星标。
- 从未来 7 天建立：进入默认清单并预填今天，或先打开编辑器选择日期。
- 从实体清单建立：进入当前清单。
- 保存按钮在第一次点击后锁定，数据库确认成功后才提示并退出。

### 9.2 完成与恢复

- 完成只改变 `done` 与 `doneAt`，不删除任务。
- 取消完成恢复原任务内容，`doneAt` 清空。
- 已完成任务可进入详情、编辑、恢复或删除。
- 归档清单中的已完成任务继续保留历史归属名称。

### 9.3 归档清单

- 归档不是删除。
- 归档清单默认退出活动清单、全部未完成、星标和未来 7 天。
- 归档详情默认只读；编辑或新增前先恢复清单。
- 恢复清单后，原任务重新进入活动查询。

### 9.4 清除已完成

- 当前清单内只清除该清单的已完成任务。
- 已完成任务总页可以清除全部，并在确认中显示数量。
- 清除采用一批操作和一个撤销记录，不逐条触发页面重画和同步。
- 批量墓碑全部收到服务端确认前，不物理删除本地数据。

### 9.5 删除任务

- 明确删除按钮二次确认；高频手势删除提供可靠撤销。
- 撤销时间以实际可恢复时间为准，不能只是 UI 定时器。
- 服务端、Android 和网页使用同一墓碑版本合同。
- 墓碑物理清理不能让长期离线设备失去校准能力。

### 9.6 删除清单

- 默认清单不可删除。
- 删除前说明任务数量与迁移去向。
- 迁移任务和删除清单在同一事务中完成。
- 其他设备应用该变更后不能留下孤儿任务。
- 清单删除本身是否提供撤销，可以后续决定；但数据一致性不能依赖用户不撤销。

## 十二、真机与跨端验收清单

## 十三、建议优先级

如果只安排一轮修复，建议严格按以下顺序：

1. **先修 500 条上行截断与确认协议。**这是静默数据丢失通道。
2. **再修删除撤销竞态。**这是用户明确看到“可以撤销”却可能恢复失败的问题。
3. **完成清单删除事务与孤儿引用保护。**确保任务永远有有效归属。
4. **修复网页未来 7 天新增。**这是已浏览器复现的直接可见 Bug。
5. **统一归档、清除和未来 7 天口径。**让首页、详情、Android 和网页表达同一件事。
6. **最后补齐删除入口、草稿、防连点和文档状态。**

在这些问题修复并验证以前，不建议扩大任务高级功能、标签体系或复杂智能清单。先让“建立以后找得到、完成以后分得清、删除以后能恢复、换设备以后不会变”成为可靠的基础合同。
